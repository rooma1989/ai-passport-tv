# 最小产品：小智电视精简版和 Muse 自建电台 —— 设计

状态：2026-11-04 草案。第 3、4、5 节主人已经逐段确认（2026-10-31）；第 6 节讲过但还没确认；第 7、8 节里标了**待确认**的部分是这份文档第一次提出来的。第 13 节的数字都是实测，没有标“推算”的都测过。

## 1. 背景和目标

项目从“一个 ESP32 小电视”长成了家庭媒体中心（RooTV：片库、网盘、YouTube、语音、手机听、多家庭……）。主人想收一下：先做**最小场景**的产品，卖给陌生用户——

- 设备：星智 Cube 1.54（ESP32-S3，8 MB 八线 PSRAM）。
- 内容：只有 **CCTV/卫视直播** 和 **B站**。
- 收费：买断，不持续收服务费。
- 主人不运营任何视频服务器，带宽和转播都不在主人这边。

这份文档定的是：一套共用的“精简版核心”，加两种部署方式——**A：用户家里的电脑**，**B：用户自己的 Muse 云电脑推到用户自己的七牛**。设备固件同时支持两种。

## 2. 已经定下、不再讨论的

| 问题 | 决定 | 依据 |
| --- | --- | --- |
| 设备能不能不靠服务器直连 CCTV/B站 | 不能 | 实测（第 13.1 节）：两家给的都是 H.264 **High** profile，乐鑫 `esp_h264` 只解 Constrained Baseline，一帧都解不出；就算换成 Baseline，360p 也只有实时的一半多 |
| 主人自己的云服务器转发 | 不做 | 带宽按每台约 0.6 元/小时（旧编码）或 0.1 元/小时（H.264），持续亏；而且由主人的服务器转播是版权风险最高的做法 |
| Muse 云电脑直接当服务器、设备连进去 | 不行 | 实测（第 13.2 节）：出网全经代理，平台没有对外端口，Cloudflare 免费隧道开不起来 |
| 卖哪种硬件 | 只卖 S3 + PSRAM 的板子 | HLS 拉流要在设备上解 H.264，C3（护照板）没有 PSRAM，做不到 |
| B站内容形式 | 频道式：按顺序循环，设备只换台 | 设备只有三个键；第一版不做点播 |
| 内置 CCTV 频道表 | 保留（主人决定） | 见第 10 节风险 |

## 3. 精简版核心（已确认）

同一份代码，打包时加一个 `EDITION` 设置：`full` 是现在的 RooTV，`lite` 是精简版（暂定名“小智电视”）。打包时写死，用户改不了。

`EDITION=lite` 时：

- 监护进程（`server/selfhost/__main__.py` 的 `build_children`）不起 YouTube 节点、网盘组件、手机听声音，也不起护照板的媒体服务。
- 中转（`server/relay/__main__.py` 的 `_serve_tenants`）跳过片库、网盘、YouTube 设置。
- 关掉的接口在 `server/relay/web.py` 返回 404；控制台读 `/api/state` 里的版本，只显示精简版有的页。
- 模块仍全部打进包里（YouTube、片库和 B站的代码互相 import，硬删容易坏）。

| 精简版保留 | 精简版关掉 |
| --- | --- |
| 设备：配对、配网、网页刷机 | 片库、网盘（OpenList） |
| 直播：内置频道表、备用线路、线路检测、台标 | YouTube |
| B站：扫码登录、关注和收藏生成频道 | 语音、手机听 |
| 基本设置；一个管理员账号，自动登录 | 多用户：用户、审计、邀请、访客 |
| | EPG、剧集、投屏、宠物、电脑上看 |

账号系统（tenancy）保留：配对和 B站登录都挂在它上面；单个家庭本来就是桌面版的常规用法。

## 4. 内置频道表和自动更新（已确认）

- **主人这边的维护工具**（每天跑一次）：读几份公开 m3u 列表，按台名归到固定频道 ID；逐条拉一帧、记格式和死活；**新出现的线路要主人在网页上看截图确认**（列表里有标错台、循环播广告的）；已确认的线路只自动查死活；生成 `channels.json`，用主人的私钥签名，放到项目的静态网站。
- **用户那边**：安装包自带一份；启动和每 12 小时拉一次，用内置公钥验签，不过就不用；频道 ID 固定，设备台号不乱跳；同一个台的几条线路在本地记成功率，优先用自家网络上好的那条（现有 `linecheck`/`linequality`）。
- 用户只能隐藏、排序，不能改线路。
- 第一版范围：CCTV1–17、各省卫视、几个少儿台，约 60 个台，排在设备频道最前面。
- 完整版继续“不带内容”，只有精简版内置。

## 5. B站频道（已确认）

- 电脑上扫码登录（现有 `bililogin`），凭证只存本机，过期前自动续（现有，**还没用真实账号测过**）。
- 登录后列出两类，用户勾选：关注的 UP 主（按最近更新排序，默认前 12 个，即 `MAX_CREATORS`），收藏夹（**新写**，默认最多 8 个）。每个一个频道，播完循环，每台设备记住每个频道播到哪。
- 设备上 OK 键打开现有菜单，加一项“下一个视频”（固件小改）。
- 画质 360p。被删、要大会员、地区限制的视频自动跳过并记日志；登录失效时设备显示“请重新扫码登录”。
- 调 B站接口限速。
- **要实测**：设备 CONFIG 包上限 7168 字节（`channel_groups.CONFIG_MAX`），约 60 个直播台 + 最多 20 个 B站频道应该放得下，但名字长短不定；放不下就截短设备上显示的名字。

## 6. 部署 A：用户家里的电脑（讲过，待确认）

- **安装**：Windows 安装包（现有 CI 的 Inno Setup）和 macOS dmg，用精简版名字。测试版不签名并配放行教程；**正式卖之前买 Apple Developer ID 和 Windows 代码签名证书**。
- **第一次打开**：自动建管理员并登录（现有），三步引导：连设备 → 看看频道（已经有了）→ 扫码登录 B站（可跳过）。Windows 安装时加防火墙放行规则。
- **设备到手**：主人发货前刷好固件；买家开热点配网，配网页里“电脑地址”由电脑程序预填（现有）；设备显示 6 位配对码，在电脑上输入（现有）。
- **新写：局域网自动找电脑**。电脑 IP 会随路由器变。设备连不上服务器超过 15 秒就发 UDP 广播“小智电视服务器在哪”，电脑程序回自己的地址和端口，设备记住再连。用 UDP 广播而不是 mDNS（Windows 防火墙下 mDNS 不可靠，见电脑客户端设计里的“未验证”）。
- **电脑关了或睡着**：设备显示“电脑没开或者睡着了”；有设备在看时电脑程序阻止睡眠（`desktop/power.py`，要确认 Windows 上生效）。
- 这种部署下设备走**现有的 TCP 推画面协议**，固件不变。

## 7. 部署 B：Muse 云电脑 + 用户自己的七牛

### 7.1 链路

```
片源（CCTV 线路 / B站）
   │  拉流
   ▼
用户的 Muse 云电脑：精简版核心（Linux 无界面）
   │  ffmpeg 转成小码率 HLS，经 HTTPS 上传（Muse 只有出网代理，正好够用）
   ▼
用户自己的七牛 Kodo 空间 ──► 七牛 CDN（用户自己的已备案域名）
   │  设备按编号取切片（HTTP）
   ▼
星智板：HLS 拉流模式（第 8.2 节）
```

主人只提供软件和教程；Muse 账号、七牛账号、实名、备案域名、超出免费额度的费用都是用户自己的。

### 7.2 推流端

- 精简版核心加一个**无界面 Linux 模式**：没有托盘、没有本机网页，配置用一个文件，加几条命令（下面 7.5 节）。Muse 跑 Python 3.12，现成的 ffmpeg 就能用。
- 输出格式（实测可用）：H.264 Constrained Baseline 240×136、20 帧/秒、约 250 kbit/s，AAC-LC 单声道 24 kHz 32 kbit/s，6 秒一个 TS 切片，每片从关键帧开始。合计约 309 kbit/s，每小时约 130 MB。
- 上传：七牛表单上传，**必须用加速入口**（华东是 `upload-z0.qiniup.com`；普通入口从 Muse 只有 26 KB/s），3 路并发，失败重试，切片设 1 天后自动删除。
- 片源断了自动重连，编号接着排（仓库外的测试脚本 `muse-probe/qiniu_push.py` v3 已实现）。**要改的**：ffmpeg 读超时从 15 秒降到约 5 秒，再配上备用线路，一条卡住就换下一条——实测里所有卡顿都来自片源卡住后等满 15 秒才重连（第 13.3 节）。
- https 片源要给 ffmpeg 加 `-http_proxy`（Muse 的出网代理），B站媒体地址就是这种。

### 7.3 七牛的几个实测约束

- **覆盖上传的文件会旧 10～20 秒**，即使 `.m3u8` 缓存设 0、请求带 `?t=`。所以设备**不依赖播放列表**。
- **404 会被 CDN 缓存**：提前请求还没上传的切片，之后切片传上去了还是拿到 404。带 `?t=<毫秒>` 的请求能绕过。
- 免费额度（实名后每月）：10 GB HTTP 下载流量、10 万次写请求。按每小时 130 MB，**10 GB 约 75 小时/月**（每天约 2.5 小时）；写请求在 7.4 节的设计下每小时约 600 次，够约 160 小时。超出由用户自己付费（国内 HTTP 约 0.24 元/GB）。
- 设备从国内拉七牛很快：6 秒一片（约 230 KB）中位 0.22 秒下完。

### 7.4 换台控制通道（**待确认**，新提出）

设备连不进 Muse，Muse 又不能 24 小时把所有台都推一遍（CPU 0.19 核/路、可用内存只有约 548 MB、流量和写请求都按量）。所以**只推设备正在看的那个台**，设备换台要能告诉 Muse。两边唯一都能访问的就是七牛：

- **设备写一个控制文件**：`<前缀>/ctl/<设备ID>.json`，内容 `{"ch": 频道ID, "session": 随机串, "seq": n, "t": 时间}`。设备用一个**只能写这一个文件**的七牛上传凭证（scope 限定为 `空间:<前缀>/ctl/<设备ID>.json`，有效期一年，到期由 Muse 续发）。凭证泄露最多只能改这个文件。
- **Muse 每 2 秒读一次**控制文件的最新版本，用七牛管理接口读、不经 CDN（具体接口实现阶段验证）。
- **每次换台用一个新路径**：Muse 把新台推到 `<前缀>/live/<session>/seg_000000.ts` 起；设备从 `seg_000000.ts` 开始带 `?t=` 取，直到拿到。新路径没有旧播放列表、也没有缓存的 404 问题，切片也不用再传播放列表（写请求减半）。
- **开播缓冲**：ffmpeg 打开一个 HLS 直播源时，会从源的最新几片往前读、而且是全速读，所以新台开头几片会很快产出——设备换台后能较快攒起缓冲。**要实测**：换台到出画面的时间，目标 10 秒以内。
- **没人看就停**：设备在播放时每 5 分钟写一次心跳；Muse 10 分钟没收到心跳就停推流，省流量和写请求。

### 7.5 用户怎么配（**待确认**）

Muse 本身就是界面：

1. 用户按教程注册七牛、实名、建公开空间（华东-浙江）、绑定自己的已备案域名，`.m3u8` 缓存设 0，建一个只管这个空间的子账号密钥。
2. 把精简版核心的发布包发给 Muse，说“按说明部署”；把七牛的五个变量交给 Muse（密钥只给 Muse）。
3. Muse 运行 `bili-login` 命令，得到二维码图片发到聊天里，用户用 B站 App 扫码。频道勾选也在聊天里说给 Muse，Muse 改配置文件。
4. Muse 运行 `device-code` 命令，生成一段**设备配置码**（CDN 地址、前缀、设备 ID、控制文件凭证）和对应二维码。用户在设备配网页里把这段码贴进“云电台”一栏。
5. Muse 装好守护（7.6 节），完成。

### 7.6 守护和恢复

Muse 的机器会不打招呼重启（实测一次，推流进程被直接杀掉）。所以：

- 推流外面套一层监护，进程挂了 5 秒内拉起；再加一个定时看门狗，宿主重启后把监护本身恢复（Muse 已按这个做过并验证）。
- 恢复后**继续用原来的前缀和会话**，编号接着排，设备只会觉得是一次短暂的缓冲。
- 守护只能减少损失，不能消除重启风险；这一点写进教程。

## 8. 设备固件：两种模式

### 8.1 TCP 推画面模式（部署 A，现有）

不变。

### 8.2 HLS 拉流模式（部署 B，原型已验证）

原型在主仓库之外的 `hls-proto/`（复用本仓库 `components/bsp`）。要搬进固件的做法：

- **取切片**：按编号取 `seg_%06u.ts`；第一次请求 404 就每秒带 `?t=<毫秒>` 重试；40 秒还没有，就写一次带新会话的控制文件，让推流端换到新路径，从新路径的 0 号重来（没有播放列表可读，这是唯一干净的重新同步）。
- **拆包和解码**：自己写的 TS 拆包（PAT→PMT→H.264 0x1B、AAC 0x0F），`espressif/esp_h264` 软解，`espressif/esp_audio_codec` 解 AAC；片源重连造成的时间戳跳变折叠成一条连续时间线。
- **播放**：声音是主时钟；画面到点再推屏，晚 150 ms 以上的帧丢掉；240×136 居中显示在 240×240 屏上。
- **缓冲**：实测落后 4 片（约 24 秒）不够扛片源的 20～35 秒空档；改成按需加深——开播先用 1～2 片起播，每卡一次把目标缓冲加 1 片，上限约 8 片（48 秒）。
- **内存**：要开 PSRAM。现在的电视固件故意关着 PSRAM（避免大块 malloc 落进 PSRAM 拖慢 SPI DMA），所以用 `CONFIG_SPIRAM_USE_CAPS_ALLOC`：只有显式要 PSRAM 的分配才进 PSRAM，TCP 模式的行为不变。原型的 PSRAM 用量约 3.3 MB，内部 RAM 剩约 40 KB。
- **Wi-Fi**：沿用电视固件现在的 Wi-Fi 管理（11 dBm 发射功率等板子上的修正）。
- **控制**：换台时写控制文件（7.4 节），播放时每 5 分钟写心跳。

### 8.3 模式怎么选

设备配网页加“云电台”一栏：贴了设备配置码就是 HLS 模式，否则是 TCP 模式（连电脑）。配置码存 NVS；状态页显示当前模式。

## 9. 出错处理

| 情况 | 设备上看到的 | 处理 |
| --- | --- | --- |
| 片源卡住或断开 | 缓冲用完后画面停住，显示“正在缓冲” | 推流端 5 秒超时重连、换备用线路；设备一有切片就接着播 |
| Muse 机器重启 | 同上，时间更长 | 守护拉起，沿用原会话 |
| 七牛 404 / 旧列表 | 无感 | 按编号取 + `?t=` 重试 |
| 设备配置码过期（控制凭证一年到期） | 换台没反应，提示“请让 Muse 更新设备配置码” | Muse 续发 |
| 免费额度用完 | 七牛开始计费（不会断） | 教程里说明；Muse 每周把用量告诉用户 |
| 部署 A：电脑睡着 / IP 变了 | “电脑没开或者睡着了” | 阻止睡眠；UDP 广播找电脑 |

## 10. 风险与决定

- **版权和广电监管**（不构成法律意见，正式卖之前找律师）：内置主人维护的 CCTV 频道表属于“持续提供片源”，有帮助侵权风险；能看直播的盒子还受广电对互联网电视的监管。部署 A、B 里拉流和分发都发生在用户自己的电脑或账号上，比主人运营服务器的风险低很多。主人已了解并决定保留内置频道表。
- **七牛内容审核**：用户的七牛账号分发直播内容，可能被封。风险在用户账号上。
- **Muse**：在国内被封，普通国内用户大多用不上——部署 B 主要面向海外华人和愿意折腾的用户。拿个人 AI 助手的云电脑长期推流，Meta 的条款是否允许不明确；机器会重启。
- **片源稳定性**：公开线路经常失效、卡顿；维护工具和备用线路是这个产品的生命线。

## 11. 测试和验收

- 第 5 节 CONFIG 包大小：60 个直播台 + 20 个 B站频道，实际名字。
- 部署 A：Windows 10/11 与 macOS 各一台，从安装到出画面；改电脑 IP 后设备自己找回来；电脑睡眠提示。
- 部署 B：一台 Muse、一个七牛空间、两台设备同时看不同的台，各 2 小时；记录卡顿次数和时长、换台时间、流量和写请求。验收线：片源正常时 0 卡顿；换台 10 秒内出画面。
- 固件：HLS 模式连续 8 小时，内部 RAM 不下降；TCP 模式在开了 `SPIRAM_USE_CAPS_ALLOC` 后帧率不低于现在。

## 12. 分阶段（建议，**待确认**先后）

1. **P1 精简版核心**：`EDITION`、内置频道表和维护工具、B站收藏导入、控制台精简。先在 Mac 上可卖。
2. **P2 部署 A 收尾**：局域网找电脑（固件 + 电脑）、Windows 包实测、首次引导、签名证书。
3. **P3 固件 HLS 模式**：把原型搬进固件，`SPIRAM_USE_CAPS_ALLOC`，配置码，自适应缓冲。
4. **P4 推流端**：核心无界面模式、七牛上传、控制通道、`bili-login`/`device-code` 命令、Muse 部署教程。
5. **P5 部署 B 端到端验收**（第 11 节）。

## 13. 实测数据

### 13.1 S3 能解什么（2026-10-31，星智板，`esp_h264` 1.5.0）

| 片段 | 结果（含缩放到 240×135） |
| --- | --- |
| B站 360p 原始流（High） | 0 帧，`profile_idc is error` |
