# 直播帧放不进字节目标时 — 设计

状态：已在分支 `degrade-fix` 上做完，2026-10-13。只改服务端；用 `tools/degrade_lab.py` 在本地片段和合成片段上离线测量过，还没有在设备上看过。

## 1. 问题

每帧直播画面是 3-3-2 调色板索引图（AI Passport 320x180，星智 240x180），切成 15 条 12 行的条带，各自 deflate 压缩，只发与设备已显示画面相比有变化的条带。每帧都必须放进字节目标：Passport 上是 `TV_RATE_START` / 帧率 = 200000 / 12 ≈ 16.7 KB。以前帧超出目标时：

- **`ladder`**（没有 numpy 时的默认）把整帧的 R、G、B 舍入到更粗的色阶，每帧重新选档。舍入总是向上（`(v + step/2) // step * step`），所以一档就让画面偏暖，相邻两帧落在不同档位时色调来回跳（蓝 ↔ 黄）。
- **`perceptual`**（有 numpy 时的默认）在颜色接近时让像素沿用已显示的值或左邻值。距离里蓝的权重最低（3、6、1），于是改动的总是蓝（偏蓝），左邻沿用连成长长的横向一串：就是设备上看到的横条拖影。`perceptual_2d` 再加上沿用上邻（竖向乱码）；`mosaic` 很糊。
- 一帧只**超出 1.6%**（CCTV1 一帧 16,934 B，目标 16,666 B），整帧都被降质。

测量中发现的一点：即使加了 `-sws_dither none`，ffmpeg 的 `rgb8` 输出也是**有序抖动**的（真实视频上奇数列平均比偶数列的 R、G 亮 8，B 最多亮 20）。凡是一对像素里只留一个的做法（mosaic 取左上角像素、复制一行），都只留下一种抖动相位而偏色；`mosaic` 和 `ladder` 偏黄一部分就是因为这个。

## 2. 测量工具（`tools/degrade_lab.py`）

- `capture VIDEO --name N --start S --seconds 6` 用服务端自己的滤镜链（`fps=12`、`frames.FIT`、`format=rgb8`、`-sws_dither none`）截出片段 `N.<宽x高>.rgb8`；`--filter` 在前面加 ffmpeg 滤镜（"drama" 片段加了胶片颗粒）。`synth` 画一段平涂色块的动画（带字幕）和一段新闻画面（背景、下方标题条、滚动字幕），走同一条滤镜链。
- `run DIR` 让每个片段过一遍 `server/degrade.py` 的 `PictureEncoder`——`live.py` 每帧调用的就是它（相对已显示画面的增量、强制刷新条带、所选模式、补发），目标取生产目标，以及让片段中位帧超出 5%、20%、50% 的目标。每个模式相对 ffmpeg 生成的帧给出：线上字节 / 目标；**偏色**（整段上每帧 R、G、B 平均误差的平均值取绝对值，取最大的通道，0..255）；**偏色闪动**（这个每帧误差的帧间变化）；**横向 / 纵向拖影**（原图没有的、8 个以上相同像素连成横向 / 纵向一串的像素占比，百分点）；**断层**（误差在条带边界上的跳变比其他行间多多少）；**陈旧**（显示的内容来自更早一帧、且与本帧有 3% 以上像素不同的条带占比，以及一条条带连续陈旧的最多帧数）；**PSNR**（整段）和 **SSIM**（8x8 亮度块）；降质帧占比、换档次数；每帧编码毫秒。输出 `results-<宽x高>.md/.json` 和对比图（原图和每个模式各一行，三帧：最贵的一帧和中位附近两帧）。
- 这里用的片段（各 6 秒、72 帧）：*corridor*（静止的监控走廊，墙上贴满海报，有人走过：文字多）、*street*（拥挤街道，细节多、运动多）、*sport*（沙漠飞车，快速运动）、*talk*（车里说话的人，有切镜）、*drama*（同一素材压暗并加动态颗粒，类似 CCTV1 的剧）、*cartoon* 和 *news*（合成）。320x180 无损中位：13.9–26.0 KB。

## 3. 试过的做法

| 做法 | 结果 |
|---|---|
| 把变化最小的条带推迟到下一帧，等满 2 帧的优先 | 代价最小的损失：超出 20% 时 SSIM 0.956，颜色和细节都没丢。但陈旧占比随超出量上升（+20% 时 16% 的条带，+50% 时 30%），断层和顿挫也随之增加，所以它只适合小幅超出，不适合大幅超出 |
| 色阶改成对称合并（2、3、4 级合成 3 等；`n1`、`n2`） | 仍偏色：实际画面里大片区域落在同一级（米色路面红绿都是 4），只动红绿不动蓝，这片就偏蓝 / 偏紫（偏色 1–4，SSIM 不如空间合并）。只作为测量选项保留（`steady_colour`） |
| 时间上保持（与已显示像素差一级以内就沿用） | 画面发花，且让控制器停在粗档；放弃 |
| 取平均而不是挑一个的空间合并：两行合一（`rows`）、一半行对合一（`rowsh`）、两列合一（`cols`）、四行合一（`rows4`） | 字节约为整帧的 0.84 / 0.61 / 0.47（`rows+cols`）/ 0.28（`rows4+cols`）；偏色 ≤ 0.5。采用 |
| 平均值恰在两级之间时怎么舍入 | 按奇偶列交替与抖动相关：蓝偏 +7…−11。伪随机：不偏，但 deflate 压不动（`rows` 只省 6–40%）。8 个一组交替：不偏、可压，但出现看得见的 8 像素竖条（蓝一级是 85）。采用：逐像素交替，每 8 个像素、每个合并行换一次相位——每种抖动相位进位、舍去各半（偏差 ≤ 0.3），图样和抖动一样细，而且可压 |
| 任何一帧超出 1.25 倍就升档，细一档放得进 0.85 倍才回 | 一个尖峰之后就一直停在粗档（生产目标下 74% 的帧降质） |

## 4. 新默认：`TV_DEGRADE=steady`

`server/degrade.py`，只用标准库。

1. **放得下就不动。**有变化（超过 1% 像素）的条带加上轮转的强制刷新条带，按当前档压缩；放得下就发，`fill` 用掉剩下的字节。
2. **小幅超出就推迟。**否则按顺序发：强制刷新条带、已等满 `MAX_WAIT` = 2 帧的条带、再按变化像素数从多到少；放不下的等下一帧。推迟的条带保持设备上原样。
3. **持续大幅超出才粗一档。**只有变化条带连续 `CLIMB` = 3 帧超过目标的 `1 + DEFER` = 1.25 倍（镜头切换由推迟吸收），并且粗一档确实更小，才升一档。
4. **带滞回地回升。**在一档停留 `DWELL` = 12 帧（1 秒）后，用当前帧试细一档，只有细一档的变化条带放得进目标的 `DOWN` = 1.1 倍才降回（1.1 到 1.25 之间不动）。仍是粗档画的条带用空余字节补回，最粗的先补。回升后 2 × DWELL 内又不得不升档，下次就多等一倍（最多 8 倍）。
5. **档位**（`rowsh`、`rows`、`rows+cols`、`rows4+cols`）：只让画面变软，不偏色、不拖影。比较内容时每条带按它被画时的档位比较，所以换档本身不会让条带被重发。
6. **强制刷新**在条带有任何变化、或设备上是更粗一档时发本帧画面，否则重发设备已有的画面，因此修复丢包不会把细档的条带换成粗档。首帧逐档变粗直到整幅放得下（都放不下就用最小的一档，没发出的条带下一帧补）。

旧模式仍可选（`TV_DEGRADE=ladder|perceptual|perceptual_2d|mosaic`），行为与之前完全一样；`TV_ENCODE=delta|fill` 也一样。

解读：`steady` 的偏色在 0.1 以下（ladder 11–15，mosaic 12–19，perceptual 2–4），偏色闪动 0.1–0.3（ladder 0.6–1.5），没有拖影（perceptual 横向 35–65 个百分点，perceptual_2d 纵向 43–70），陈旧条带只占 2–5%、最多连续 2 帧，在每种超出程度下 SSIM 都高于所有旧模式。只推迟（`defer_only`）的 SSIM 更高，但在 +20% / +50% 时每帧有 16% / 30% 的条带是陈旧的（断层 0.7 / 1.5，闪动 0.8 / 1.5）：适合小幅超出，`steady` 也正是这样用它的。`TV_STEADY_DEFER=0.4`（`steady_d40`）用更多陈旧（6–12%）换更少的变软，值得在设备上试。240x180 的片段只有 8–16 KB，生产目标下从不超出；几种超出情形下的排序相同。

## 6. CPU

单进程，Apple M1 Pro，7 个片段在生产目标及 +20% / +50% 下，只计编码（`live.py` 每帧做的那次调用）：

| 模式 | 每帧毫秒（平均） | p95（各次平均） | 最差 p95 |
|---|---|---|---|
| `steady` | 3.5 | 5.9 | 10.5 |
| `defer_only` | 3.2 | 3.8 | 7.1 |
| `ladder` | 7.8 | 9.9 | 26.1 |
| `perceptual` | 13.5 | 17.4 | 24.6 |
| `perceptual_2d` | 17.4 | 23.1 | 30.6 |
| `mosaic` | 5.5 | 6.6 | 9.1 |

`steady` 的耗时约为 `perceptual` 的四分之一（后者在 12 帧/秒时让 1 vCPU 主机上整个 Passport 媒体进程用了约 40% CPU）、`ladder` 的一半，而且不需要 numpy。大部分时间花在压缩变化的条带上；降一档多 1–3 ms（行列取平均用 131072 项的查表，每个进程在第一个频道开始时建一次，约 0.2 秒）。

## 7. 没做的 / 要在设备上确认的

- 在两块板子上用繁忙的频道和 CCTV1 看 `steady`，与 `TV_DEGRADE=ladder`（主机上现在的临时设置）对比。
- 片段来自本地和合成；真实直播帧可以在主机上用同一条滤镜链截取，再用 `tools/degrade_lab.py run` 跑。
- 没有修 `perceptual`：有了 `steady` 就用不着它，保持原样以便对比。
